# 检索基线

## 测试设置

- 语料索引：`corpus/.index`（maplibre-native，2,228 文件 / 17,450 切块）
- 查询集：`data/tickets/synthetic_tickets.json`，64 条合成工单
- 检索：`HybridRetriever`，Top-10，意图固定为 `defect`（自然语言）与 `localize`（符号）
- 重排：词法回退（本地交叉编码器未安装）

## 结果

| 指标 | 数值 |
|---|---|
| 符号召回 Recall@10 | **0.516**（64 条） |
| 自然语言召回 Recall@10 | **0.000**（64 条） |
| 命中通道分布 | bm25 146 次 / graph 51 次 / vector 0 次 |

分类型自然语言召回：用法 0.0、视觉 0.0、崩溃 0.0、性能 0.0。

## 分析

1. **符号召回 0.516**：查询直接使用 `root_cause_symbol`，BM25 能命中同名符号所在切块。未命中的一半主要因为合成工单里的符号名是虚构的（语料中不存在对应实现），并非检索缺陷。
2. **自然语言召回为 0**：工单症状是中文，代码语料是英文标识符；在没有向量通道的情况下，BM25 与符号图都无法跨越语言鸿沟。
3. **图谱通道贡献 51 次命中**：说明"从命中符号沿调用边扩展"确实能把相关切块带出来，只是无法解决语义匹配。

## 下一步

向量通道是唯一能补上跨语言缺口的手段，但需要先把 17,450 个切块向量化：

- 调用 `qwen3.7-text-embedding`，每批 20 条，约 873 次请求；
- 按 0.5 元/百万 token 估算费用约 45–60 元，按 8 并发约 20–25 分钟；
- 完成后重新运行本脚本，把 `natural_language_recall_at_10` 作为新基线，并单独记录向量通道贡献。

在向量通道接入前，本基线应被视为**下界**，不应据此判断检索架构优劣。
